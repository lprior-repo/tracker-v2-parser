# Native PostgreSQL performance contract

The workload runs on a shared 16 GiB Mac with an 8 GiB scraper stack target. Changes must preserve exact result identities, retained source evidence, manual research, access stops, the shared three-acquisition budget, page/domain/receipt atomicity and durable workflow recovery. A configured 3 RPS ceiling is an admission limit, not a throughput guarantee.

## Query and transaction boundaries

Two additive MileSplit HASH indexes support exact source-result ID and source-URL reconciliation. Original source, equality, JSON kind/mask, order and limit predicates remain authoritative; PostgreSQL rechecks hash collisions. HASH avoids a B-tree tuple-size failure on untrusted long identifiers. No uniqueness or historical result-key assumption is introduced. A raw meet row is inspected only if the exact lookup reaches it; unlinked observations are retained.

Result reference caches are transaction-local, positive only, and bounded to 128 performances and 1 MiB per chunk. Missing references retain the original lookup/error behavior. No cache crosses a page or an identity merge/split. Domain upserts remain ordered and atomic. Queue batching preserves duplicate precedence, sequence consumption, access stops, contact discovery and refresh behavior. Review writes use exact change guards. School ordering addresses the tested reversed-school writer pattern; it does not establish deadlock freedom for arbitrary research/identity transactions.

Immutable capture/parse digests and reference serialization are calculated before obtaining the page transaction locks. Their errors are consumed at the original validation points, after retained receipt replay checks. Domain writes, checkpoint success, receipt and attempt/operation completion remain one transaction. A single boxed action boundary bounds compiler type complexity without spawning detached work.

## Sparse results and concurrent revisions

SQL blank detection uses the same Unicode whitespace set as Rust's `str::trim`. A sparse replay preserves published event, mark, metadata and failure-status evidence consistently across scalar columns and merged result projections. Nonblank strings remain verbatim. The retained source response can still record a newly captured blank; it is distinct from the effective published facts used for normalization.

A sparse read that finds no result cannot rely on `SELECT FOR UPDATE` to protect the absent key. Its first upsert permits insertion but suppresses a conflicting update. PostgreSQL locks the conflicting row even when the `ON CONFLICT DO UPDATE` condition is false. The writer then reads the locked row, recalculates normalization and school evidence, and retries once. Existing-row sparse writes retain their row lock, and complete/batched writes use ordinary unique-key conflict locking. This preserves changed-event units and explicit failure statuses without adding an advisory lock per observation. See PostgreSQL's [Read Committed rules](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED) and [INSERT conflict conditions](https://www.postgresql.org/docs/18/sql-insert.html#SQL-ON-CONFLICT).

MileSplit raw revisions serialize by proven published-file identity before adoption, domain writes and revision reconciliation. Distinct lock IDs are acquired in sorted order in one query and remain held through the page transaction. The lock namespace includes the current schema; a page accepts at most 64 distinct proven files, while a normal raw capture identifies one file. Pages without a proven raw file incur no file-lock query. This protects URL aliases of the same published file and retains superseded observations for review. It does not establish deadlock freedom for every other identity or research workflow.

Run `cargo test --locked --test result_whitespace_replay --test concurrent_result_writes -- --nocapture` with an isolated PostgreSQL test database. The concurrency scenarios coordinate actual database waits, enforce finite deadlines, verify stored values and ownership, and replay durable receipts without further mutations. The assigned sparse scenario exercises the public persistence contract; the unassigned and raw-file scenarios also exercise the source parsers.

## Identity, contact and queue concurrency

Concurrent conflicting updates to linked profiles can both decide to split from the same canonical athlete. After the existing update of that canonical row, a separate statement removes it only when it has no source profiles and no results. The fresh statement sees the competing committed split after the canonical-row wait. Profile-owned reviewed identity history and reviewed-result records remain retained. This cleanup introduces no new profile/canonical lock order; it does not claim to eliminate existing identity-merge deadlocks.

Contact captures serialize by the schema-scoped `(source, school_id)` identity before reviewing previous office claims, saving schools or updating coach claims. One transaction advisory lock protects a contact revision even when its school does not yet exist. Lock acquisition is a separate statement so later claim queries use a fresh Read Committed snapshot after waiting. The lock lasts through the page transaction and receipt commit, and is released on rollback. Non-contact pages add no contact lock query. Source captures remain retained; superseded claims receive review notes, and an unconfirmed office mailbox is withdrawn.

Non-contact, non-refresh checkpoint rediscovery uses `ON CONFLICT DO NOTHING`. A no-op conflict UPDATE would still lock the existing row, unnecessarily waiting for a checkpoint owner and potentially completing a cycle with shared profile writes. The insert-only path also applies to non-contact items in a mixed contact batch. Explicit refresh behavior, contact alias suppression, duplicate precedence, affected counts and sequence consumption retain their prior contracts. This avoids locks on already committed duplicate rows; PostgreSQL may still wait for a competing uncommitted insertion of the same unique key.

Run `cargo test --locked --test concurrent_identity_split --test concurrent_contact_revisions --test concurrent_checkpoint_enqueue --test persistence_batches -- --nocapture` with isolated PostgreSQL schemas. These cases exercise overlapping splits, retained review history, coach and office revisions, checkpoint ownership, actual parsed profile navigation, receipt replay and queue parity.

## Review export scope and public evidence

Review selection compares requested and stored state values with the same Unicode whitespace and case normalization used by athlete/issue exports. Acquisition-state precedence and displayed source evidence remain authoritative. An invalid reviewed result link stays visible in its represented-school or acquisition-page scope as well as the current target scope. The invalid-link phase uses `EXISTS` predicates and retains one issue per result when multiple selected states match.

A retained PR row marked with the JSON boolean `masked: true` is not evidence that a public mark was captured. Masked-only profile evidence therefore keeps the source-availability review diagnostic when progression is restricted. Missing, null and non-boolean legacy mask metadata retain the existing unmasked interpretation; the query does not infer or recover a hidden mark.

Run `cargo test --locked --test export_review_state_scope --test export_review_masked_profile --test reviewed_result_links --test review_source_unavailable -- --nocapture` to verify state normalization, transfer invalidation, deduplication, parser-derived masked evidence and legacy mask values.

## Export observation count guards

The observation preflight counts at most 10,001 output rows to reject an athlete above the 10,000-observation limit before record aggregation. Its ownership branches use `UNION ALL`: the direct branch requires a physical athlete-source owner, while `valid_reviewed_result_links` excludes every physically owned result. Primary and unique keys prevent duplicates within either branch. These rules make the branches disjoint; changes to reviewed ownership must revisit this proof and the export regressions. A distinct union could consume the full input while deduplicating before the outer limit.

The November 21 PostgreSQL 18.1 fixture, using 4 MiB `work_mem`, produced identical counts for ten empty, below-limit, exact-limit, over-limit, mixed-ownership and reviewed-only cases. For one athlete with 100,000 physical observations, the original plan consumed all 100,000 result rows and recorded 5,642 query-level shared-buffer hits; the revised plan consumed 10,001 result rows and recorded 568 hits. Three alternating trials measured median execution times of 40.830 ms and 3.324 ms. Rust compilation ran concurrently, so these timings describe this fixture only and establish no production throughput improvement. `UNION ALL` permits early termination; it does not guarantee bounded scans for every planner choice or data distribution.

Run `cargo test --test export_count_guard -- --nocapture` with `TEST_DATABASE_URL` set to an isolated test database. The scenarios exercise public export snapshots, exact count limits, reviewed-only observations and a reviewed result that later acquires a physical owner. For plan reproduction, use `tests/export_count_guard/seed.sql` as the body of a prepared statement with `(text, integer, integer)` parameters: fixture label, physical count and reviewed count. Seed `('large-owned',100000,0)`, analyze the four affected tables, and prepare `src/database/export_snapshot_count_guards.sql` with a `bigint[]` parameter containing the returned athlete ID. Compare `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON, TIMING OFF)` with the observation union set to `UNION` and `UNION ALL`, alternating their order and checking exact count equality. Keep fixtures in a private schema and roll back the enclosing transaction.

## Sampled persistence evidence

Every sixteenth positive checkpoint ID emits fixed-label timing records. Domain stages distinguish replay preparation, contact review, school writes, school conflicts, profiles, results, unassigned results, contacts, revision review, queue insertion and checkpoint update. Durable stages distinguish pool acquisition plus BEGIN, reservation locking, receipt lookup, domain persistence, receipt writes and final COMMIT. Timings use a monotonic clock and include failed stages. They contain no SQL text, parameter values, credentials, capture bodies or full source URLs. PoolAndBegin is not presented as pure pool wait; the journal commit stage is not presented as fsync alone. Counters and retained journal samples remain the independent throughput evidence.

## Retention and cold evidence

The November 1 inventory counted 1,908,482 observations: 1,626,333 raw meet rows lacked a linked athlete profile and 282,149 came from profile URLs. Result keys identify source observations independently of campaign generation. Unknown identity or graduation year is not evidence that an observation is obsolete.

There is no approved age-based deletion rule. Cold evidence remains recoverable in the database and immutable artifacts. Exact indexed fact lookups and narrow reference projections form the hot path. Do not rewrite the approximately 4 GiB athlete-source TOAST payload merely to reduce the relation-size display. Any future physical archive must inventory result/profile/school links, reviewed identities, export references, durable captures/parses, retry lineage and later cohorts; prove restored equality before removing a live reference. This upgrade performs no retention deletion or wholesale JSON backfill.

## Resource policy

Retain the SQLx pool cap of eight, PostgreSQL connection cap of forty and global work_mem of 4 MiB. The coverage selector uses a short read-only transaction with local work_mem of 16 MiB. Its restored-snapshot alternating trial reduced median latency from 969 to 845 ms and eliminated temporary-file I/O; real PostgreSQL tests verify restoration of the pooled backend's 4 MiB default after success, failure and cancellation. The optimized selector preserved all 10,292 ordered candidates and reduced the preceding baseline median from 2,076 to 977 ms before the local-memory change.

The 512 MiB shared-buffer trial removed buffer reads without a convincing latency gain under whole-host compression churn, so the 128 MiB baseline remains. A larger candidate requires separate measurement. Whole-host compression/swap deltas, available disk and runtime latency decide acceptance; summed backend RSS is not unique physical memory. Selection batching saved only two startup queries per 2,000-page rolling batch and could change greedy exclusions, so it was withheld; no frontier cache or planner override is installed.

Prepare configuration from fresh read-only PostgreSQL 18 observations, exact prior-file SHA256 and private owned files. Preserve existing preload entries, add pg_stat_statements only during a backed-up controlled restart, and verify effective settings and pending_restart afterward. Query metrics stay private. Maintain durability settings on. Per-table autovacuum/analyze changes require relation-specific churn evidence; avoid blanket VACUUM FULL, REINDEX, statistics resets or planner forcing.

## Capacity and recovery

Build artifacts may live on the dedicated external build cache. Private recovery data must use encrypted storage with ownership enabled. The encrypted recovery container and its private local key are separate; the live PostgreSQL data directory, WAL and Restate journals remain in place. Validate both backup-destination and actual live-data filesystem headroom before operations. Native backup preflight budgets twice the database, twice retained evidence/artifacts/exports, and a 2 GiB reserve; do not assume compression savings.

Every rollout requires all six Moon lanes, exact executable hashes, an isolated PostgreSQL restore, native Restate restart/replay/export and reopened workbook equality. Scheduler/admission command changes additionally require an old-worker partial journal replay through the same invocation and a versioned future continuation. Existing input bytes and recorded journal prefixes must remain unchanged. Keep the prior worker, configuration and recovery backup until post-handoff HTTP completions, frozen-input/prefix equality, five-ledger inventory equality and publication hashes are verified.

## Live acceptance

Use the existing ten-minute heartbeat for bounded 1/5/10-minute wire starts, at most 30 completed page-stage samples and 120 recent selector pairs, plus short read-only PostgreSQL wait/counter deltas with reset timestamps. Record phase mix and export gaps. Compare paired evidence after each accepted slice; database fixture speedups are not live RPS claims. Stop extra diagnostics when capacity or runtime latency is unsafe. State completion still requires the exact retained terminal report, verified receipt/publication/delivered workbook and a quiescent predecessor before submitting the next state once.
